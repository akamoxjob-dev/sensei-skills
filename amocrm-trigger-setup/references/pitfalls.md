# Ловушки запроса сохранения

Запрос: `POST /ajax/settings/pipeline/leads/<id воронки>/save`, тело `application/x-www-form-urlencoded`, заголовок `X-Requested-With: XMLHttpRequest`, куки сессии. Ответ: `{"status":"success","response":{"result":{"actions":{"add":[…],"update":[…],"delete":[…]}}}}` либо `{"status":"fail","error":"…"}`.

Всё ниже получено опытом на тестовой воронке 18.11.2026 — около 110 запросов с правильными и нарочно кривыми триггерами.

## 1. Чего нет в запросе — удаляется

В `actions` уходит полный список триггеров воронки. Триггер, которого в списке нет, сервер удаляет и честно пишет его id в `delete`. Так удаляется и встроенный блок «покупатель» на успешном этапе.

Блок этапов (`statuses`) можно не присылать — этапы остаются как были. Скрипт его не присылает.

## 2. Отказ — целиком

При `status: fail` не сохраняется ничего из запроса. Один кривой триггер из десяти — не встанут все десять.

## 3. «Успех» не значит «сделано»

Сервер отвечает `success` и при этом:

| Что прислали | Что произошло |
|---|---|
| Неизвестное действие | ничего не создано, `add` пуст |
| Этап другой воронки или несуществующий | ничего не создано |
| Событие с несуществующим id | создан с событием «после перехода или создания в этапе» |
| Неизвестный тип условия | условие выброшено, триггер без условий |
| Числовое поле «со значением и оператором» | условие выброшено |
| Неизвестный оператор у текстового поля | сохранён как есть, условие не работает |
| Отрицательная задержка | сохранена положительной |
| Изменение несуществующего поля | триггер сохранён, ничего не делает |
| Триггер в занятую клетку | стоявший там триггер сдвинут ниже |
| Тег в «Редактировать теги» только по названию | триггер сохранён без тегов (см. п. 4) |

Отсюда правило: после записи перечитать воронку и сверить каждый новый триггер с заданием. Скрипт сверяет число условий, событие, задержку и пометку об ошибке; не сошлось — откат.

## 4. Сломанный триггер блокирует воронку

Триггер «Редактировать теги» без тегов сервер создаёт, но при следующем сохранении сам же отклоняет: «Не указано ни одного тега». После этого воронка не сохраняется вообще — ни запросом, ни из интерфейса — пока сломанный триггер не убрать.

То же делает интерфейс со своими кривыми триггерами: «Изменить поле» без выбранного поля не даёт сохранить воронку («empty fields»).

Если человек жалуется «воронка не сохраняется» — прочитай триггеры и ищи сломанный: теги без тегов, изменение поля без поля, удалённый бот.

## 5. Как пересылать существующие триггеры

Чтобы старые триггеры пережили запись, их пересылают такими, какими прочитали. Но с двумя поправками — без них сервер их портит.

- **Булевы значения — только `1` и `0`.** Строку `"false"` в настройках сервер читает как «да». Проверено: после пересылки блока «покупатель» с `false` в виде текста у него включились все галочки.
- **Подпись виджета — отдельным полем `name`.** В данных она лежит в `settings.widget_info.name`, а сервер ждёт её в поле `name` верхнего уровня и без него стирает. Проверено: карточка триггера Sensei после пересылки без `name` стала пустой.

С этими поправками пересылка не меняет ничего: 61 триггер одиннадцати типов, две пересылки подряд, в ответе `update: []`.

Сервер при любом обновлении сам убирает из настроек автора триггера (`created_by`). Так делает и интерфейс. На работу триггера это не влияет.

## 6. Что сервер проверяет честно

Несуществующий тег, пользователь, вариант списка, поле в условии; адрес вебхука; этап в «Смене статуса»; удалённый бот; слишком большая задержка; текст вместо числа в бюджете; «Смена статуса» без задержки. На всё это приходит `fail` с понятным текстом по-русски.

## 7. Не API

Запрос внутренний. amoCRM его не документирует и вправе менять. Признаки, что он изменился: скрипт не находит данные на странице, сервер отвечает не JSON, после записи сверка не сходится. Во всех трёх случаях скрипт останавливается или откатывает. Обходить это не нужно — нужно заново снять, что шлёт интерфейс.

## 8. Новая воронка или новый аккаунт: первая запись «не подтверждается»

В новом аккаунте и в только что созданной воронке встроенный блок «покупатель» (`link_customer`, успешный этап) хранится не со всеми настройками. Первое же сохранение воронки — нашим запросом или из интерфейса — дописывает ему значения по умолчанию. Сверка скрипта видит это как «изменились существующие триггеры: … (link_customer)», снимает новый триггер и пишет «ОТКАТ НЕ ПОДТВЕРЖДЁН».

Это не поломка. Проверено 24 и 25.11.2026: после такого отката в воронке остаётся блок «покупатель», новый триггер снят, повторный запуск того же задания проходит с `ok: true`.

Что делать:

1. Прочитай воронку заново.
2. Убедись: в списке изменившихся был только `link_customer`, блок «покупатель» на месте, лишних триггеров нет.
3. Запусти то же задание ещё раз — один раз.

Изменился любой другой триггер или повтор снова не подтвердился — остановись и попроси человека открыть настройку воронки.
