# Цифровая воронка amoCRM: что на каком этапе запускается

Ты разбираешь автоматизации чужого аккаунта amoCRM. Список воронок, этапов и полей даёт API amoCRM. А вот **триггеры цифровой воронки** — «сделка пришла в этап → поставить задачу, запустить бота, перевести дальше, запустить процесс Sensei» — через API не отдаются. Их видно только в интерфейсе. Этот скилл достаёт их из браузера одним скриптом, без кликов по воронкам.

## Что нужно

- Браузер, которым ты управляешь (расширение Claude в Chrome, DevTools MCP или другой инструмент, умеющий выполнить JavaScript на странице).
- Аккаунт amoCRM открыт в этом браузере, и человек в нём авторизован. Логин и пароль вводит человек сам — ты их не спрашиваешь и не вводишь.
- У пользователя есть право открывать настройку воронки (обычно это администратор).

Если браузера нет или входа нет — так и скажи. Не подменяй триггеры догадками по названиям этапов.

## Порядок работы

1. Открой в браузере любую страницу аккаунта: `https://<аккаунт>.amocrm.ru/`. Убедись, что это нужный аккаунт: назови человеку его адрес.
2. Выполни на странице `scripts/dp-triggers.js`. Это одна async-функция:
   - инструмент принимает функцию — передай её как есть;
   - инструмент принимает выражение — оберни: `window.__dp = await (<функция>)();`.
3. Вывод большой (на заполненном аккаунте сотни триггеров). Если инструмент обрезает ответ, сохрани результат в `window.__dp` и читай по частям: сначала `summary`, `pipelines`, `problems`, потом триггеры одной воронки.
4. Проверь себя до того, как пересказывать:
   - `problems` пуст;
   - число триггеров по каждой воронке совпало с числом карточек на странице (проверка ниже).

   У задачи не путай две вещи: `delay_sec` — через сколько сработает триггер, `task.deadline` — срок самой задачи.
5. Расскажи человеку простыми словами: воронка → этап → что происходит. Названия бери из интерфейса («Создать задачу», «Salesbot»), а не коды (`create_task`, `send_chat_message`).

Скрипт **только читает**: запросы `GET` с куками текущей сессии к самому аккаунту. Ничего не меняет.

## Проверка, что прочитано всё

После скрипта выполни на той же странице:

```js
const out = [];
for (const p of window.__dp.pipelines) {
  const html = await fetch(`/settings/pipeline/leads/${p.pipeline_id}`, { credentials: "same-origin" }).then((r) => r.text());
  const cards = new DOMParser().parseFromString(html, "text/html").querySelectorAll(".digital-pipeline__business_processes[data-id]").length;
  out.push({ pipeline: p.name, cards_on_page: cards, read_by_script: p.triggers });
}
JSON.stringify(out);
```

Числа должны совпасть в каждой воронке. Не совпали — скажи человеку, в какой воронке расхождение, и не выдавай список за полный.

## Что отдаёт скрипт

- `pipelines` — воронки: id, название, сколько этапов и триггеров; сколько источников сделок и их названия; включены ли «Неразобранное», контроль дублей, скоринг.
- `triggers` — по записи на триггер: воронка, этап (`pipeline_id` + `status_id`), ряд, действие, событие, задержка, условия, настройки. У задачи — тип по названию, текст и срок. У триггеров на чаты — в каких источниках они срабатывают.
- `stage_hints` — подсказки этапов: что менеджеру написано под названием этапа.
- `stage_events` — включённые события этапа («входящее письмо → перевести в этот этап»).
- `warnings` — мёртвые ссылки: триггер пишет в поле или проверяет поле, которого в аккаунте уже нет.
- `summary` — итоги и отпечаток для сверки двух чтений.
- `problems` — воронки, которые не прочитались. Пусто — значит, прочитано всё.

`warnings` показывай человеку отдельно: это готовые находки аудита — автоматизация стоит, но ничего не делает.

Поля триггера, словарь действий и событий: `references/output.md`.

## Чего скрипт не видит

Говори об этом прямо, когда отдаёшь карту:

- **Что внутри Salesbot.** Виден только факт запуска и имя бота. Шаги бота — отдельный экран.
- **Что внутри процесса Sensei.** Виден id процесса и «запустить / остановить». Сам процесс читай через MCP-сервер Sensei.
- **Что делает чужой виджет.** Видны его код и настройки триггера, логика — на стороне виджета.
- **Настройки левой колонки.** Скрипт отдаёт названия источников сделок и «включено / выключено» для «Неразобранного», контроля дублей и скоринга. Сами правила дублей и скоринга он не разбирает.
- **Цифровую воронку покупателей.** Скрипт читает воронки сделок. На странице воронки покупателей такого блока нет, этим способом она не читается.
- **Существует ли бот.** У триггера Salesbot видны id и имя бота на момент настройки; удалён ли бот с тех пор, скрипт не проверяет.
- **Запуски не из воронки:** вебхуки, кнопки в карточке, боты в чатах, внешние интеграции.

## Правила

1. **Только чтение.** Не нажимай «Сохранить» в настройке воронки и не шли запрос сохранения. amoCRM сохраняет воронку целиком: одна ошибка в запросе затрёт этапы и триггеры. Подробности — `references/save-request.md`. Менять триггеры можно только по прямой просьбе человека и через интерфейс.
2. **Чужие данные остаются у человека.** В настройках триггеров бывают адреса вебхуков с ключами, тексты задач, имена сотрудников. Не отправляй их во внешние сервисы и не вставляй в публичные тексты.
3. **Не выдумывай.** Действие, которого нет в словаре, покажи как есть, с его кодом и настройками, и скажи, что не знаешь его точного названия.
4. **Это не API.** Скрипт опирается на внутреннюю разметку интерфейса amoCRM. После обновления amoCRM он может перестать находить блок — тогда он честно вернёт `problems`, а ты скажи об этом человеку.

## Как склеить с остальным

Триггер ссылается на этап парой `pipeline_id` + `status_id`, на поле — `field_id`, на процесс Sensei — `sensei.process_id`. По этим id он склеивается с данными API amoCRM (воронки, этапы, поля, пользователи) и с процессами из MCP-сервера Sensei. Так получается карта аккаунта: что запускается на каждом этапе и что этот запуск делает дальше.
