# Что отдаёт `dp-triggers.js`

## Запись о триггере

| Поле | Что это |
|---|---|
| `trigger_id` | id триггера в amoCRM |
| `pipeline_id`, `pipeline` | воронка |
| `status_id`, `stage` | этап, на котором стоит триггер. 142 — «Успешно реализовано», 143 — «Закрыто и не реализовано» |
| `row` | ряд в сетке цифровой воронки (сверху вниз, с 1) |
| `also_on_stages` | есть только у «широкого» триггера, растянутого на несколько этапов: остальные его этапы. В данных такой триггер один |
| `action` | что делает триггер, код — см. словарь ниже |
| `handler` | `amocrm` — встроенное действие; `widget:<код>` — действие виджета |
| `title` | подпись триггера, если её дал виджет |
| `event` | когда срабатывает — см. словарь событий |
| `event_options` | уточнения события, когда они есть: `talk_creation_type` (`inbound` — входящим сообщением), `chat_sources` и другие |
| `chat_sources` | в каких источниках чата срабатывает: id и название. Нет поля — «в любом источнике» |
| `delay_sec` | задержка триггера в секундах: 300 = «через 5 минут» |
| `work_time`, `date_exec`, `recurrent` | «только в рабочее время», точная дата, повтор — появляются, только когда заданы |
| `conditions` | условия «для всех сделок, у которых…»; нет поля — условий нет |
| `settings` | настройки действия без пустых значений |
| `task` | только у задачи: `type` — тип задачи по названию (на карточке триггера написан именно он), `text` — текст, `deadline` — срок задачи, `responsible` — кому |
| `moves_to` | только у смены этапа: куда переводит (`pipeline_id`, `status_id`, название) |
| `sensei` | только у триггера Sensei: `process_id`, `direction` (`start` / `stop`), `close_tasks` |

`process_name_at_setup` у Sensei — название процесса на момент настройки триггера. Процесс могли переименовать: верь `process_id`, название сверяй через MCP-сервер Sensei.

## Условия

Каждое условие — группа:

- `type` — `tag` (теги), `custom_field` (поле), бывают и другие (ответственный, бюджет, источник);
- `field_id`, `name` — какое поле, если условие по полю;
- `logic` — `or` или `and` внутри группы;
- `values` — значения: `operator` (`equal`, `contains` и другие), `id` / `name` / `value`.

Триггер с условием срабатывает не на всех сделках этапа. В пересказе это обязательно: «ставит задачу, если поле «Форма» равно …».

## Действия

Видел в живых аккаунтах и сверил с интерфейсом:

| Код | В интерфейсе | Главное в `settings` |
|---|---|---|
| `create_task` | Создать задачу | `task_text`, `task_type`, `responsible_user`, срок (`deadline-*`) |
| `send_chat_message` | Salesbot | `bot_id`, `bot_name` |
| `change_status` | Смена статуса | `pipe_id`, `status_id` → вынесено в `moves_to` |
| `change_tags` | Редактировать теги | `tags`, `action` (`link` — добавить) |
| `change_field_value` | Изменить поле | `fields`: `field_id`, `value` |
| `change_responsible` | Сменить ответственного | `responsible_id`, `user_name` |
| `close_tasks` | Завершить задачи | `task_type`, `task_close_time` |
| `create_lead` | Создать сделку | `pipe_id`, `status_id`, какие поля копировать |
| `link_customer` | блок «покупатель» на успешном этапе | — |
| `send_widget_hook` | действие виджета (так подключён Sensei) | `widget.settings` |

Есть в списке действий amoCRM, но в данных я их пока не встречал — код назван по списку, поля настроек не проверены: `send_email` (Отправить письмо), `send_hook` (Отправить webhook), `create_and_fill_form` (Генерация анкеты), `business_bot` (Businessbot), `delete_files` (Удалить файлы).

## События

| Код | В интерфейсе |
|---|---|
| `lead_status_changed` | «После перехода в этап» — сверено |
| `lead_appeared_in_status` | «После перехода или создания в этапе» — сверено |
| `call_in` | «При входящем звонке» — сверено |
| `talk_created` | новая беседа в чате; «в любом источнике» или в выбранных (`chat_sources`) |
| `lead_added` | сделка создана в этом этапе |

Подписи двух последних названы по смыслу кода, с интерфейсом дословно не сверены. Если от подписи зависит вывод — открой триггер в интерфейсе и прочитай строку «Выполнить: …».

## Воронка (`pipelines`)

Кроме id, названия и числа триггеров:

- `lead_sources`, `lead_source_names` — источники сделок из левой колонки;
- `unsorted_enabled` — включено ли «Неразобранное»;
- `duplication_control_enabled`, `scoring_enabled` — включены ли контроль дублей и скоринг (сами правила не читаются).

## Подсказки этапов (`stage_hints`)

Текст, который менеджер видит под названием этапа: `level` и `text`. Полезно для карты: в подсказках часто написано, что на этапе положено делать руками.

## Предупреждения (`warnings`)

Триггер ссылается на поле, которого нет в списке полей аккаунта на этой же странице — скорее всего, поле удалили, а триггер остался. На карточке такого триггера в интерфейсе после «Изменить поле:» пусто. Проверяются поля в «Изменить поле» и в условиях. Существование ботов, тегов и пользователей не проверяется.

## Счётчик amoCRM

`amocrm_triggers_count` — число, которое сам интерфейс держит как «количество триггеров». Оно не обязано совпасть с числом объектов: на одном аккаунте было 149 при 153 триггерах, на другом 2 при 9. Что именно он считает, я не выяснил. Полноту проверяй по карточкам на странице, а не по нему.

## События этапа (`stage_events`)

Отдельно от триггеров у этапа есть «входящее письмо / звонок / заход на сайт / чат → перевести сделку в этот этап». Скрипт отдаёт только включённые. На аккаунтах, где я проверял, все они были выключены, поэтому эту часть вывода на живых данных я не видел.

## Отпечаток

`summary.fingerprint` — число, посчитанное по набору триггеров (id, этап, ряд, действие, задержка). Два чтения одного аккаунта дают одно число, если триггеры не менялись. Удобно, чтобы сверить два прогона или заметить, что между аудитами что-то поменяли.
