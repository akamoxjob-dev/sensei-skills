# Как amoCRM сохраняет цифровую воронку — и почему этот скилл ничего не пишет

Это справка, чтобы понимать риск. Ставить триггеры запросом умеет соседний скилл `amocrm-trigger-setup` из этой же ветки — со сверкой после записи и откатом.

## Что происходит по кнопке «Сохранить»

Интерфейс шлёт один запрос:

```
POST /ajax/settings/pipeline/leads/<id воронки>/save
Content-Type: application/x-www-form-urlencoded
X-Requested-With: XMLHttpRequest
```

В теле — **вся воронка целиком**, а не одно изменение:

- `statuses[i][…]` — каждый этап: id, название, цвет, порядок, события этапа;
- `actions[i][…]` — каждый триггер воронки:
  - у существующего есть `id`;
  - у нового вместо `id` временный `cid`;
  - внутри: `action`, `handler_code`, `statuses[]`, `row`, `delay`, `execution_condition[…]`, `conditions_groups[…]`, `settings[…]`;
- служебные поля (`enable_loss_reasons` и другие).

В ответ приходит, что сервер сделал с триггерами:

```json
{"status":"success","response":{"result":{"actions":{"add":[…],"update":[…],"delete":[]}}}}
```

## Почему это опасно

Проверено на тестовой воронке 18.11.2026, около 110 запросов:

- **Чего нет в запросе — удаляется.** Прислал один новый триггер без старых — сервер создал его и удалил все остальные.
- **«Успех» не значит «сделано».** На кривой триггер сервер часто отвечает `success` и молча делает не то: ничего не создаёт, выбрасывает условие, подставляет другое событие.
- **Один сломанный триггер блокирует воронку.** После него она не сохраняется вообще, даже из интерфейса.
- **Формат внутренний.** amoCRM его не документирует и может поменять без предупреждения.

Подробно — `amocrm-trigger-setup/references/pitfalls.md`.

## Что делать

- Читать — скриптом из этого скилла. Это безопасно.
- Ставить новые триггеры — скиллом `amocrm-trigger-setup`, по прямой просьбе человека и после его «да».
- Удалять и править существующие триггеры — через интерфейс.
- Не собирать запрос сохранения руками.
