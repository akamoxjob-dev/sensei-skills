# Как amoCRM сохраняет цифровую воронку — и почему не слать этот запрос самому

Это справка, чтобы понимать риск. Не инструкция «как ставить триггеры запросом».

## Что происходит по кнопке «Сохранить»

Интерфейс шлёт один запрос:

```
POST /ajax/settings/pipeline/leads/<id воронки>/save
Content-Type: application/x-www-form-urlencoded
X-Requested-With: XMLHttpRequest
```

В теле — **вся воронка целиком**, а не одно изменение:

- `statuses[i][…]` — каждый этап: id, название, цвет, порядок, события этапа;
- `actions[i][…]` — каждый триггер воронки:
  - у существующего есть `id`;
  - у нового вместо `id` временный `cid`;
  - внутри: `action`, `handler_code`, `statuses[]`, `row`, `delay`, `execution_condition[…]`, `conditions_groups[…]`, `settings[…]`;
- служебные поля (`enable_loss_reasons` и другие).

В ответ приходит, что сервер сделал с триггерами:

```json
{"status":"success","response":{"result":{"actions":{"add":[…],"update":[…],"delete":[]}}}}
```

## Почему это опасно

Сервер сравнивает присланное с тем, что у него есть. Присланное считается новым состоянием воронки. Отсюда:

- забыл включить в запрос существующий триггер — рискуешь его удалить;
- ошибся в блоке этапов — рискуешь переименовать, переставить или потерять этап, а на этапах лежат сделки клиента;
- формат внутренний: amoCRM может поменять его без предупреждения.

Запись запросом я **не проверял** — только видел, что шлёт интерфейс при обычном сохранении. Что именно сервер сделает с неполным запросом, неизвестно.

## Что делать

- Читать — скриптом из этого скилла. Это безопасно.
- Менять триггеры — через интерфейс, по прямой просьбе человека, с проверкой глазами до «Сохранить».
- Если всё же нужна массовая расстановка запросом: сначала на пустой тестовой воронке; тело собирать из полного текущего состояния той же страницы; до и после снимать отпечаток скриптом чтения и сравнивать список триггеров. На клиентском аккаунте — только после такого прогона и с согласия владельца.
