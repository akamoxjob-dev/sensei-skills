# Карта проекта: воронка, кнопки задач, переходы

Ты рисуешь человеку, как на деле работает одна воронка amoCRM, в которой сделку ведут процессы Sensei. Результат — доска Whiteboard. Глядя на неё, человек понимает: на каком этапе какой процесс, какие кнопки у менеджера в задаче, куда каждая кнопка уводит сделку, какие поля процесс требует заполнить и что сломано.

## Главное

- **Карта — это граф переходов, а не колонки по порядку этапов.** Сделка прыгает между этапами по кнопкам задач: из «В работе» сразу в «Счёт выставлен», из «Квалификации» сразу в «Демонстрацию». Первая версия карты колонками по порядку этапов была непонятна заказчику — не повторяй её.
- **Кнопки берёшь из схем опубликованных процессов**, а не из названий этапов и не из порядка в воронке. Для этого читаешь каждый основной процесс: задача → кнопка → куда ведёт.
- **Одна воронка за раз.** Не назвали — спроси какую.
- **Только чтение.** В amoCRM и Sensei ничего не меняешь. Пишешь только на доску.
- **Сначала читаешь всё, потом одним проходом пишешь доску скриптом** `scripts/board_layout.py`. Не рисуй доску руками по блоку.
- В отчёте честно скажи, что не проверено.

## Что нужно

- MCP-сервер Sensei, подключённый к нужному аккаунту. Сверь аккаунт: `account_dictionary`, раздел `account`, назови его человеку.
- Браузер с открытым аккаунтом amoCRM — для триггеров цифровой воронки (скилл `amocrm-digital-pipeline` из ветки `amocrm` этого репозитория).
- Желательно токен API amoCRM (обычно в `.env` проекта: `AMOCRM_DOMAIN`, `AMOCRM_TOKEN`) — для порядка этапов, обязательных полей и сотрудников. Нет токена — порядок этапов и обязательные поля возьми в браузере и скажи, откуда.
- Инструмент Artifact с типом Whiteboard и инструмент ArtifactData.

## Порядок работы

1. **Аккаунт и воронка.** Сверь аккаунт, уточни воронку.
2. **Этапы и обязательные поля** (API amoCRM, только GET):
   - `GET /api/v4/leads/pipelines/<id>` — этапы с `sort`: порядок этапов;
   - `GET /api/v4/leads/custom_fields?limit=250&page=N` — у поля `required_statuses`: на каких этапах amoCRM требует его заполнить. Это «Обязательно в amoCRM» на карточке этапа.
3. **Триггеры воронки** — скилл `amocrm-digital-pipeline`. Нужны триггеры Sensei этой воронки: какой процесс на каком этапе запускается и при каких условиях. Обычно триггеры запускают процессы только на входе, дальше сделку ведут сами процессы.
4. **Карта Sensei** — `account_map` без раздела, до статуса `ready` (около двух запросов на включённый процесс; скажи человеку цену). Потом раздел `processes` с `process_id` и `names: true` для процессов, которые запускают триггеры, и для тех, кого они вызывают (`calls`). Из строки берёшь:
   - `fw` — поля, которые процесс пишет: это жёлтый блок карточки. Служебные отметки вида «<процесс> запущен», «Дата и время …» можно опустить;
   - `to` — в какие этапы процесс переводит сделку;
   - `out` — исходы; `un` — то, что лежит в недостижимой части: это не работает, не выдавай за рабочее.
5. **Схемы основных процессов** — главный шаг. Для каждого процесса воронки:
   ```
   get_process_draft  process_id=<id>  detail="skeleton"  limit=200
                      fields=["id","element_type","refs","edges.caption","edges.item_next"]
   ```
   - В ответе `is_draft: true` — значит, это черновик. Перечитай с `version_id=<deployed_version_id>`: на сделках работает опубликованная версия.
   - Найди элементы `task` с несколькими стрелками — это кнопки. По каждой подписи (`edges.caption`) иди по `item_next` через «Изменить поле», формы и условия, пока не встретишь:
     - `status` с `refs` «moves the deal to stage …» — кнопка переводит сделку в этот этап;
     - `process` с `refs` «starts process …» — запускает следующий процесс (он и поставит следующий этап);
     - `end` — процесс закончился; его подпись — исход;
     - стрелку назад к той же задаче — «повтор».
   - Мультиусловие по счётчику недозвонов пиши одной строкой: «Не дозвонились → повтор, на N-й раз Закрыто».
   - Процессы, которые решают сами, без кнопок (распределение, мультиусловие по источнику), опиши по веткам: «импорт → Распределение».
   - Если процесс работает на нескольких этапах сразу и у этапов нет своих кнопок, это «узел»: зелёная карточка, а у этапов пиши «Своих кнопок нет: сразу запускается …».
6. **Проблемы** — то, что видно по ходу, плюс по просьбе:
   - `audit_missing_fields` — удалённые поля и этапы. Считай только достижимые (`reachable`).
   - Неактивные сотрудники: `GET /api/v4/users` (`rights.is_active`), потом `find_usages` по ним, до 10 за вызов. Каждый вызов перечитывает все процессы — несколько сотен запросов. Делай по просьбе или когда сотрудники явно важны.
   - Триггер запускает выключенный процесс.
   - **Название этапа не совпадает с тем, что на нём делает процесс.** Пример: кнопка «Счёт согласован» ставит этап «Оплачено», а процесс на нём ждёт подписанный договор. Это всегда находка — в отчётах по этапам будет путаница.
   - Кнопка ведёт в удалённый этап; черновик с неопубликованными правками; большая недостижимая часть процесса.
7. **Описание доски** — собери `spec.json` (формат ниже) по прочитанному.
8. **Доска.**
   - Новая: `Artifact` с `action: "quickstart"`, `intent: "other"`, затем публикация типа Whiteboard с `type_url` из ответа, `title` «Воронка <название>», `auto_open: "after_first_write"`. Дальше — инструкции типа.
   - Если в контексте доски есть `claim` — сначала запиши `board/claim-<claim>` с областью, в конце запиши его `{}` (с `if_version`).
   - `python scripts/board_layout.py spec.json <папка> [--start N]` → файлы элементов, `meta.json` и `writes.json` (готовые пачки по 50).
   - `ArtifactData` `batch` по каждой пачке из `writes.json`, потом `board/meta` из `meta.json`. Документ уже существует — нужен `if_version`.
   - Перерисовываешь свою доску: сначала `list` `elements` (с `out_dir`) — страница сама двигает элементы и меняет их версии; удаляй и правь с текущими версиями. Новые id — выше самого большого e-номера (`--start`).
9. **Отчёт человеку.** Ссылка на доску; что на ней; главные находки; что не проверено (выключенные процессы, Salesbot, виджеты, настоящие ночь и выходные и т. п.). Доску глазами не проверяй, если не попросили: так велят инструкции типа.

## Как выглядит доска

- **Заголовок** — «Воронка «<название>»: куда ведёт каждая кнопка», подзаголовок одной строкой, легенда справа.
- **Полосы.** Главный путь — слева направо. Ответвления (подготовка КП, осмотры) — полосой ниже, под тем этапом, откуда в них уходят. Вторая половина воронки (договор, оплата, отгрузка) — отдельной полосой снова с левого края.
- **Входы и тупики.** Этапы, куда сделка приходит снаружи, собери в начале карты. Этапы, из которых её не выводит ни один процесс, вынеси отдельной полосой «Тупики».
- **Синяя карточка этапа:**
  ```
  **Название этапа**
  Обязательно в amoCRM: <поле>            ← если есть
  Процесс: [имя](ссылка в конструктор)
  **Кнопки:**
  - Кнопка → куда
  - Дальняя кнопка → **этап**              ← дальний переход жирным
  - Не дозвонились → повтор, на 4-й раз Закрыто
  - Отказался → Закрыто
  ```
- **Под карточкой:** жёлтый блок — поля, которые заполняет процесс; розовые блоки — проблемы.
- **Зелёная карточка** — процесс без своего этапа (узел), со своими кнопками.
- **Колонка справа «Куда сделка уходит из воронки»:** «Закрыто и не реализовано» (обязательные поля, триггеры на закрытии), другие воронки (кто туда отправляет), общие процессы недозвона.
- **Стрелки** — только между соседями. Туда и обратно — одна стрелка с `head: both`. В «Закрыто» стрелки не рисуй: туда ведёт почти каждая карточка, это пишется текстом. Дальние переходы — жирным в тексте кнопки.
- **Без молчаливых разрывов.** У этапа без входящей стрелки напиши на карточке строку «Как попадает: …», у этапа без исходящей — «Как уходит: …»: триггером с этапа, процессом, руками. Не нашёл — так и напиши: «не нашёл».
- **Не больше четырёх цветов:** синий — этап, зелёный — узел, жёлтый — поля, розовый — проблема; колонка выходов — белая.
- **Не пиши id и коды** в тексте карточек: только названия, как в интерфейсе.

## Описание доски (`spec.json`)

Пример — `scripts/example_spec.json` (воронка выдуманная).

```jsonc
{
  "title": "Воронка «…»: куда ведёт каждая кнопка",
  "subtitle": "Сделка прыгает между этапами по кнопкам задач",
  "board_title": "Воронка …",                       // имя доски
  "constructor_url": "https://my.sensei.plus/constructor/<id аккаунта Sensei>/",
  "lanes": [                                        // полосы сверху вниз
    { "title": "Вход, квалификация, КП",
      "nodes": [
        { "key": "work", "col": 2,                  // колонка: шаг 450 px
          "text": "**Взят в работу**\nПроцесс: [Новый лид](P:12345)\n**Кнопки:**\n- …",
          "fields": "Тип товара · Город · …",    // жёлтый блок, необязательно
          "problems": ["…"],                        // розовые блоки, необязательно
          "kind": "hub" }                           // только для зелёного узла
      ] }
  ],
  "exits": { "title": "Куда сделка уходит из воронки", "col": 7, "lane": 0,
             "blocks": [ { "text": "**Закрыто и не реализовано**\n…", "problems": [] } ] },
  "arrows": [
    { "from": "work", "to": "qual" },                                   // справа налево, соседи в полосе
    { "from": "work", "to": "prep", "from_side": "bottom", "to_side": "top" }, // прямо вниз, та же колонка
    { "from": "qual", "to": "prep", "route": "below_from" },           // вниз в соседнюю колонку
    { "from": "insp", "to": "sent", "route": "above_to", "head": "both" },
    { "from": "hub",  "to": "req",  "route": "gap:2" }                 // через просвет перед полосой 3
  ]
}
```

- `(P:12345)` в тексте скрипт превращает в ссылку на процесс в конструкторе.
- Стрелка вниз из колонки выходит из последнего блока колонки (жёлтого или розового), а не из карточки: иначе она пройдёт сквозь блоки полей.
- `route` ставь, когда стрелка идёт вниз в другую колонку. Две такие стрелки, которые сходятся в одной точке, разведи: одной `below_from`, другой `above_to`.
- Колонку выходов ставь правее последней колонки той полосы, где она стоит. Скрипт предупредит, если она наползёт на следующую полосу.
- Высоту блоков скрипт считает по длине текста. Слишком маленький блок страница рисует больше, поверх соседей, — поэтому не подгоняй размеры руками.

## Грабли

- **Инструмент браузера отдаёт около тысячи символов за ответ.** Сожми данные прямо на странице (коды вместо слов, строка на этап) и читай кусками по `slice`. Не выводи строки вида `ключ=значение&…`: такой ответ блокируется как куки.
- **Страницу настройки воронки по токену API не читай:** правила безопасности такое блокируют. Триггеры — только через браузер.
- **`out_dir` у `ArtifactData`** с коротким путём Windows вида `C:\Users\ABCD~1\…` отклоняется — пиши полный путь.
- **Консоль Windows** не в UTF-8: в своих проверочных скриптах вызывай `sys.stdout.reconfigure(encoding="utf-8")`. Флаг `python -I` игнорирует `PYTHONIOENCODING`.
- **`find_usages` с новым набором целей перечитывает все процессы** — собирай до 10 целей в один вопрос.
- **Дата последнего запуска** в Sensei хранится около года. Процесс с запусками, но без даты, скорее всего, не запускался больше года.
- **Поля из `fw`** — это то, что процесс пишет: формой менеджера или сам. Карта Sensei их не различает — так и скажи человеку.

## Чего не делать

- Не раскладывай этапы колонками по порядку воронки как основную форму карты.
- Не рисуй стрелки в «Закрыто».
- Не выдумывай кнопки и переходы: только из прочитанной схемы опубликованной версии.
- Не пиши в amoCRM и Sensei: ни триггеров, ни процессов.
- Не клади в этот скилл и в примеры данные клиентов: названия компаний, имена, id, поддомены.
